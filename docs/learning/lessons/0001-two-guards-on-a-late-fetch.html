Two guards, one fetch

FEAT-002 Ticket 3 · Checkpoint 1 · client/src/pages/NotePage.tsx

The win: by the end you can explain why CP1 needs two separate guards (the stale flag and the serverReply.id tag), and what breaks if you delete either one.

Step 1What CP1 does

When you open /notes/:id, the page asks the server for that note's body and shows it. That's the whole job. The hard part is that you can switch notes while a request is still in flight, so replies can arrive late, or out of order.

  const [serverReply, setServerReply] = useState<{ id: string; body: string }>()
  useEffect(() => {
    if (!noteIdFromUrl) return
    let stale = false                                  // guard 1
    void getNoteFromServer(noteIdFromUrl).then(
      (noteDetailOrNull) => !stale && setServerReply({ id: noteIdFromUrl, body: noteDetailOrNull?.body ?? '' }),
      () => {},
    )
    return () => { stale = true }                      // cleanup
  }, [noteIdFromUrl])

  const serverBody = serverReply && serverReply.id === noteIdFromUrl ? serverReply.body : undefined   // guard 2
  const shownBody = (noteIdFromUrl && localBodies[noteIdFromUrl]) ?? serverBody
  ...
  if (shownBody === undefined) return null

Step 2When the effect and its cleanup run

The effect runs after the first render, and again every time noteIdFromUrl changes. React calls the cleanup before it runs the effect again, and once more when the page goes away (react.dev).

Each run gets its own stale variable. So opening note A, then note B, gives you:

You doReact runsA's staleB's stale
open Aeffect (A): request Afalse
open Bcleanup (A), then effect (B): request Btruefalse

From now on, A's reply is ignored whenever it arrives, because the callback checks !stale. This is the exact pattern react.dev uses, with the flag named ignore: “If the userId changes from 'Alice' to 'Bob', cleanup ensures that the 'Alice' response is ignored even if it arrives after 'Bob'” (Fetching data).

Step 3Why one guard isn't enough

stale stops a future setServerReply from running. It can't undo state that's already set. Right after you switch from A to B, serverReply still holds A's body from earlier. B's request hasn't answered yet, so nothing has replaced it.

That's what guard 2 is for. The body is stored with the ID it belongs to, and the page uses it only if serverReply.id === noteIdFromUrl. Otherwise serverBody is undefined, which means “still loading”, and the page renders nothing for a moment.

The two bugs

No stale flag: a late reply for an old note overwrites the new one.
No ID tag: in the gap before the new reply arrives, the old body shows on the new page.

Step 4Break it yourself

Turn the guards off and on, open notes, and deliver the replies in any order. Try to finish both tasks.

    • Turn off only the ID tag. Make Bio's page show Chem's body.
    • Turn off only the stale flag. Make Bio's page lose its own body after it showed it.

    Step 5The other lines

    LineWhy it's there
    if (!noteIdFromUrl) returnuseParams types it as possibly undefined. With no ID, there's nothing to fetch.
    void getNoteFromServer(…)Starts the request without awaiting it. An effect can't be async, because it must return its cleanup, not a promise.
    noteDetailOrNull?.body ?? ''null means 404 Not Found. The note is in your list, so its create (POST) just hasn't reached the server yet. Show an empty body.
    () => {}Any other failure is swallowed, so the page stays blank. Ticket 4 adds retries.
    localBodies[noteIdFromUrl] ?? serverBodyUntil autosave (Ticket 4), your unsaved local copy wins over the server's.
    shownBody === undefined → nullRenders nothing while loading. An empty box would let you type into it, and your typing would become the local copy that hides the server's body forever.
