# Retro: FEAT-002 Ticket 1 (Checkpoints 4–6 + demo)

Date: 2026-10-14. Covers CP4 controller (`279da27`), CP5 service (`9348253`), CP6 repositories
(`8a2bc2b`), the end-to-end demo, and ticking off Ticket 1 (`7f7c17d`).

Ordered by severity. Nothing here has been actioned yet. Suggested start: #1, then #2.

## 1. 🔴 No automated guardrail

**What happened:** there is no CI workflow (no `.github/workflows`), no pre-commit hook, and no
`lint`/`typecheck` script. `tsc` and `vitest` ran this session only because the agent ran them by
hand. CP6 was committed on "just commit it" with nothing automated in the way.

**Fix:**
- Add a `"typecheck"` script (`tsc --noEmit` plus the client's type-check) so the hook and CI share one command.
- Pre-commit hook (the `setup-pre-commit` skill) runs `typecheck`. The tests need the local DB, so they
  don't belong in the hook.
- GitHub Actions job: `supabase start`, then `npm test`.

## 2. 🟡 Steering files contradict and duplicate each other

**What happened:**
- `CLAUDE.md` says checkpoints are "at most 50 lines each". The `checkpoint-piece-by-piece` memory
  says "length as needed, not trimmed to 50 lines". An agent has to guess which one wins.
- `checkpoint-piece-by-piece` ("show each piece and get an OK") is replaced by
  `design-before-reveal` ("reveal all the code at once"), but its index line still loads every
  session as live advice.
- `quiz-before-commit`, `design-before-reveal` and the named-status-code rule are each written in both
  `CLAUDE.md` and memory, so they have two sources of truth.

**Fix:** delete `checkpoint-piece-by-piece`, and decide the 50-line rule once, in `CLAUDE.md`. Cut the
duplicated memories down to only what `CLAUDE.md` doesn't carry: the reasons and the user-specific gotchas.

## 3. 🟡 `run-campi` starts duplicate servers and only knows the auth flow

**What happened:** step 2 launches servers without checking for running ones. The servers from an
earlier session were still on 3100/5173, so the new API died with `EADDRINUSE` and Vite moved to
5174. The agent had to read logs and kill the duplicates. The Ticket 1 demo then needed an ad hoc
Playwright script, because the skill only drives sign-up/login/logout.

**Fix:**
- Step 2 starts with `curl -s -m 2 localhost:3100/health` and skips the launch if it answers.
- Add `scripts/notes-flow.mjs`: sign up → click New page → assert 201 Created → screenshot → query
  the `notes` and `blocks` rows. Then each ticket's **Demo** line can be run by one command.

## 4. 🟢 Sub-agent briefs written by hand twice per checkpoint

**What happened:** for every checkpoint, the agent wrote out a long description for
`backend-reviewer` and again for `checkpoint-quizzer`. The same facts are already in
`docs/tickets/FEAT-002-notes.md`.

**Fix:** add a pointer to both agent files: "read the checkpoint's section in `docs/tickets/`
(named in the prompt)". The prompt then only needs the user's description plus any decisions made
during the session.

## 5. 🟢 Ticket plan named a function that couldn't do the job

**What happened:** the ticket's CP6 listed `findNoteOwner(id)`, but a 200 OK retry has to return
the whole note, so it was replaced by `findNoteWithBody` during the CP5 design. The CP6 reviewer
later found the left join can match more than one top-level text block (deferred to Ticket 3:
`order by b.position limit 1` + a test).

**Fix:** these are judgement calls, so no new lint rule. Possible tweak to the planning/grill step:
check that each repository function can produce the response shape its endpoint promises.
