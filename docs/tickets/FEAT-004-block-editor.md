# FEAT-004 - block editor (TipTap)

**Sprint:** 2 · **Branch:** `feature/block-editor` (from `main`) · **Created:** 2026-10-21

Replaces the earlier plain-text bullet-list plan (branch `feature/bullet-lists`, deleted). Comes
**before** FEAT-003 blurting.

## Context

The note body is plain text in a `<textarea>` (`NoteEditor`), saved as **one `text` block** per
note (FEAT-002). The `blocks` table was designed for a real block editor: `type` (`text`,
`heading`, `list_item`), nesting through `parent_id`, fractional `position` per sibling group.

**Goal:** replace the textarea with a TipTap editor whose content is stored as real blocks, then
add dot and numbered lists that continue and nest as you type, like Google Docs.

**Out of scope:**
- Dash lists, headings, inline formatting, links, tables, images. Each can be its own feature.
- Concurrency (removed from the roadmap). `blocks.version` stays unused.
- Questions pointing at blocks. Stable block ids keep that possible later.
- Converting existing notes: all current data is test data and gets wiped.

## Shared decisions (grilled 2026-10-21)

| # | Area | Decision |
|---|---|---|
| 1 | Block types | Paragraph = `text` block `{ text }`. List item = `list_item` block `{ text, style: 'bullet' \| 'numbered' }`. `heading` is rejected for now. |
| 2 | Lists in storage | Items only, no container rows. Consecutive `list_item` siblings form a list. Nested items are children through `parent_id`. **No migration.** |
| 3 | Block ids | Generated by TipTap's UniqueID extension and **stable across saves**. |
| 4 | API | `blocks` replaces `body` everywhere. `GET /api/notes/:id` → `{ id, title, blocks, updated_at }`. `PUT` takes `{ title, blocks }`. Creating a note makes **no** blocks (TipTap shows an empty paragraph; the first save writes it). |
| 5 | Payload shape | Nested tree, order = array order: `[{ id, type, properties, children? }]`. The server generates `parent_id` and `position`. |
| 6 | Validation (`PUT`) | Note must be the user's (404 Not Found). 400 Bad Request when: not the tree shape; `id` not a UUID; `type` not `text`/`list_item`; `text` not a string; `list_item` without a valid `style`; children on a non-`list_item` or a non-`list_item` child; duplicate ids; an id that belongs to a **different** note; depth over 9. Bodies over Express's 100 KB limit → 413 Content Too Large. Unknown `properties` keys are stripped, not rejected. Shape checks (400) run before the ownership check (404); neither reveals whether the note exists. No cap on block count: the 100 KB body limit bounds it. |
| 7 | Saving | One `sql.begin`: (1) move the note's blocks to temporary positions, (2) upsert the tree in order, parents before children, with the new positions, (3) delete the note's blocks missing from the tree. Deletes come last so a re-parented block isn't caught by its old parent's cascade. |
| 8 | Keys | TipTap defaults (`* `, `- ` and `1. ` start lists; Enter continues; Enter on an empty item moves out; Tab/Shift+Tab nest). One override: **Tab on a paragraph inserts 4 spaces**. |
| 9 | Markers | CSS per level: dots `•→◦→▪`, numbers `1.→a.→i.`. |
| 10 | Drafts | `campi.draft.<id>` holds `{ title, blocks }`; `removeDraftIfSaved` compares blocks by `JSON.stringify`. Old `{ title, body }` drafts fail the shape check and are ignored. |
| 11 | Testing | Back-end acceptance tests (Vitest + Supertest). The editor itself is checked with a manual browser checklist (no front-end test setup). |
| 12 | Workflow | Same as FEAT-001/002 (see CLAUDE.md). Blast-radius tags below are estimates; re-check each when its plan is presented. |

## Ticket 1: TipTap editor saved as blocks (paragraphs only) 🔴

**Slice:** open a note → the body is a TipTap editor → type a few paragraphs → reload → the same
paragraphs come back, each stored as its own `text` block with the same id as before.

🔴 because it changes the shared note contract (`body` → `blocks`) across client, controller,
service and repository, and adds client dependencies.
